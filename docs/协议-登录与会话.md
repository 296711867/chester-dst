# DST 登录流程（C 层逆向还原）

> 分析对象：`dontstarve_steam_x64.exe`（Steam 版，7.7MB，全明文）
> 用途：登录（账号获取）→ 加入服务器握手 → 会话校验 全链路还原
> 日期：2026-08-29

---

## 0. 一句话总结

登录分**两段**：
1. **账号登录**：客户端向 Klei 拿 Steam 票据 → `POST /login/LoginViaSteam` → Klei 返回 `Token`（GameSessionToken）+ `UserID`（KU_/OU_）+ `Username` + `AnalyticsJWT`；
2. **入会话校验**：加入服务器时把 Token 随握手发给主机，主机回查 Klei `POST /login/GameSessionToken` 验证 `Token` 真伪与平台 ID 一致性，成功后才把 `ClientUser` 标记为已验证。

Steam 票据（SteamTicket）**只用于向 Klei 证明"你是这个 Steam 号"**，不进游戏会话；游戏会话内一律用 Klei 的 GameSessionToken。

---

## 1. 关键对象

### 1.1 cSteamAccountCommunication（登录控制器）
- 构造：`0x1402CD270`（`new 0x1C0`）→ 构造函数 `0x1402CD120`
- `+0x128` 指向 Account/session 对象（SetAccountInfo / SetGameSessionToken 的目标）
- `+0x130` = **当前请求类型**（决定走哪个 /login 端点 & 响应怎么解析）
- `+0x134` 结果/标记、`+0x136` 响应 ok 位
- `+0x140` = HTTP 请求管理器指针
- `+0x1A0/+0x1A8` = Steam 票据缓冲区（malloc 0x800，`0x14017e990`）
- `+0x1B0` = Steam auth ticket handle（`GetAuthSessionTicket` 返回）
- `+0x1B4` = 票据实际长度
- `+0x1B8` = 待处理动作状态（3=LoginViaSteam / 0xa=RegisterSteamAccount / 0xe=ServerLoginTokenViaSteam / 0xb=纯 Login）
- 成员回调对象（Steam 回调注册点）：`+0x148`→`0x1402CC8A0`、`+0x168`→`0x1402CC9D0`、`+0x188`→**`0x1402CCA30`（Steam 票据回调）**

### 1.2 全局
- `qword_140674FC8` = Account/Session
  - `+0x088 / +0x260` = Klei userid 字符串（KU_/OU_）
  - `+0x100` = 用于 TokenPurpose 校验的 "Game" 字段名表
  - `+0x1F8` = 平台 NetId 对象（写进握手包）
  - `+0x1D0` = Steam 票据/Cookie 字符串（票据回调里写入）
- `g_NetManager`（+0x308 client 标志 / +0x309 server 标志 / +0x30A 游戏中标志 / +0x30B **online 模式标志** / +0x2A4 版本号 / +0x2A8 平台号）

### 1.3 登录端点枚举 → 路径（`0x1402CC650`）
```
enum 3  -> /login/LoginViaSteam
enum 0xa -> /login/RegisterSteamAccount
enum 0xe -> /login/ServerLoginTokenViaSteam
enum 0xb -> /login/Login  （经典用户名/密码）
```
注意：这里有**两套独立的端点枚举**，不要混淆——
- cSteamAccountCommunication 请求类型（`+0x130`，响应分派用）：2=Login / 3=LoginViaSteam / 4=Logout 类 / 6=TokenPurpose / 0xa=RegisterSteamAccount / 0xd=ChangePassword 类 / 0xe=ServerLoginTokenViaSteam
- HTTP 管理器路径枚举（`0x140297830` 的 path 表，服务端 GameSessionToken 校验用）：6=GameSessionToken
```
通用 /login/ 路径表（rdata，0x140575F40 起，按下标取）：`/None /login/GameSessionToken /login/ReportUser /login/RecoverPassword /login/RegisterGameKey /login/ChangePassword /login/TokenPurpose /login/LogoutAll /login/Logout /login/Login /login/CreateAccount`
Steam 附加端点：`/login/LoginViaSteam`(0x14057C6F8)、`/login/RegisterSteamAccount`(0x14057C710)、`/login/ServerLoginTokenViaSteam`(0x14057C730)
主机：`login.kleientertainment.com`

## 2. 阶段一：账号登录（客户端）

### 2.1 请求 Steam 票据
入口 `0x1402CCCD0`（= SteamLogin / RegisterSteamAccount 共用发起点，从 Lua 经绑定调用）：
1. 若 `+0x1B8 != 0` → 日志 `SteamLogin - Conflicting with existing pending steam action %i`，失败返回（防重入）
2. 检查 Steam 对象可用（`lea 0x140627DF8; call 0x140517770` 取单例；`[rax]` 非空）
3. 复制入参：`+0x38` ← 游戏名（"Don't Starve Together"）、`+0xB0` ← 主机描述
4. `+0x1B8 = 3`（状态：LoginViaSteam）
5. `GetAuthSessionTicket(buf=+0x1A8, 0x800, &+0x1B4)`（vtable `[rax+0x68]`）→ handle 存 `+0x1B0`
6. 日志 `[Steam] Auth Session Ticket requested...`
7. Steam 异步回调 `OnGetAuthSessionTicketResponse` → 派发到 **`0x1402CCA30`**

### 2.2 票据回调，组装 body（`0x1402CCA30`, "[Steam] Got Auth Session Ticket"）
1. 检查 `[rdx+4] == 1`（k_EResultOK），失败则 `RegisterSteamAccount - OnValidateAuthTicketResponse Failure!`
2. 票据原始字节 → 字符串（`0x140294400`），写入 `qword_140674FC8 + 0x1D0`
3. 按 `+0x1B8` 状态组装 JSON body（`0x1404d9c00` 起是 JSON 对象；`0x1404da1b0` 追加键值）：

| 状态 | 端点 | JSON body |
|---|---|---|
| 3 LoginViaSteam | `LoginViaSteam` | `{"SteamTicket":<ticket>,"Game":"Don't Starve Together","FriendlyHostDescriptor":...,"NoEmail":true,"TokenExpiry":<int>}` |
| 0xa RegisterSteamAccount | `RegisterSteamAccount` | `{"Username":...,"Password":...,"SteamTicket":<ticket>,"appid":"322330","Game":...}` |
| 0xe ServerLoginTokenViaSteam | `ServerLoginTokenViaSteam` | 同 LoginViaSteam（dedicated 服务器自动登录） |

4. `call 0x140298D30`（SendRequest）

### 2.3 发送 HTTP 请求（`0x140298D30` cSteamAccountCommunication::SendRequest）
1. 复用检查：`cSteamAccountCommunication::SendRequest Clobbering current response`
2. 若类型 ∈ {2,3,6}：清空 Session token 区（`qword_140674FC8+0x8` 置 0、`+0x10` 清空）
3. URL = vtable `[rbp+0x90]`（用 `0x1402CC650` 解析端点路径 + 拼接主机）；method = **"POST"**；body = JSON
4. `0x1401874f0`（HTTP 队列）注册回调 **`0x1402989D0`**
5. `+0x130 = 类型` 记录本次请求

### 2.4 响应处理（`0x1402989D0` → `0x140297B50` OnAccountCommunicationResponse）
- 包装层：HTTP 成功 && 状态码==200 → `[ctx+0x136]=1`
- `0x140297B50` 按 `+0x130` 分派（跳表 0x140298994，index = type-2）：

| 类型 | 端点 | 成功处理 |
|---|---|---|
| 2 | Login | 取 `Token` → `0x140247510`(SetGameSessionToken，写 Account+0x100) → SetOnlineMode(true) |
| **3** | **LoginViaSteam** | 取 `Token`、`UserID`、`Username`、`AnalyticsJWT` → `0x140296EE0`(SetAccountInfo：写入 Account 的 +0x38 用户名 / +0x88 **userid** / +0xB0 JWT / +0xD8 token，并 `0x140248390` SetUserId) → SetOnlineMode(true)（`0x14022E390`）→ 本地完成回调 `0x140263ED0` → `Logging in as %s` |
| 4 | Logout/改密 | 清 Token |
| **6** | **TokenPurpose** | 取 `Token`、校验 `Game=="DontStarveTogether"`、取 `Username/UserID/AnalyticsJWT` → SetAccountInfo → SetOnlineMode(true)；若 `+0x34` 挂起标志置位则执行完成回调 |
| 0xa | RegisterSteamAccount | （注册后自动登录） |
| 0xd | ChangePassword/Recover | 清 Token |
| **0xe** | **ServerLoginTokenViaSteam** | 取 `Token` → **写 `cluster_token.txt`** 到集群目录（"Please copy this file in the cluster directory of your server."） |

- 失败：取 `ErrorCode` → `[%i] Account Failed (%i): "%s"`；空 ErrorCode 时 dump 原响应 `[Warning] Empty error code received, dumping response:`

> 即：**主菜单登录成功后，KU_/OU_ userid + 会话 Token 都已落在 Account 对象**（qword_140674FC8，userid 在 +0x088/+0x260）。加入服务器时 Token 由握手带往主机。

## 3. 阶段二：加入服务器 → 握手 → 会话校验

### 3.1 客户端发握手（`0x14022F940` / 现版 0x14022F4CA，"Client connected" 前）
`ID_DST_HANDSHAKE_CLIENT_INFO`（wire 0x91）bitstream 序列化（含如下字段）：
- 消息类型 0x91
- **NetId**（`qword_140674FC8+0x1F8` → WriteNetId 0x14022BBC0）
- 显示名（0x14022E1E0 → WriteString）
- **Klei userid**（`qword_140674FC8+0x260` c_str → WriteString）
- **GameSessionToken**、metrics blob（Lua `GetClientMetricsData()`，`0x1402bac50`）
- 网络 vtable `+0x98` 发送（reliability，性能/信息 order 直接看主机端）

### 3.2 主机收握手（`0x140244795` 起，"Client connected from %s%s <%s>"）
1. 反序列化（**以主机端为准**）：str0(=在线校验用的 **GameSessionToken**，写入 `[rsp+0x78]`）→ **NetId**（`0x14022b840`，`[rsp+0x4c0]`）→ str1(**Klei userid**，`[rsp+0x70]`) → str2(显示名等，`[rsp+0x60]`) → metrics blob（`0x1402bae00`，`[rsp+0x80]`）
2. 任一字段失败 → kick `0x9b`（ID_DST_INCOMPATIBLE_PROTOCOL_VERSION）
3. 建 **ClientUser**：`new 0x3D8`（`0x14017e990`）→ ctor `0x1402968e0`（拷 guid）→ `0x140295550`(SetNetId) / `0x140295530`(SetUserIdString → +0x1C0) → flags `+0x244 |= 0x10` → metrics `+0x2F0` → AddPreAuth 进 Session 双向映射 + 分配 slot bit
4. 分支 `g_NetManager+0x30B`（**是否 online**）：

**Online（要联网验证）→ `0x140247B00` ValidateGameSessionToken(+0x30B 生效)**
```
参数: (account, client-token字符串, client-NetId字符串, userid字符串, peer, guid)
流程: vtable[rcx+0x80] → 核心 0x140298A70
  0x140298A70: 要求 IsServer(+0x309)
    - token 为空 → 直接 kick 0x94 (ID_DST_GAME_SESSION_AUTH_FAILED)
    - 否则组 { "Token": <client token> } JSON body
    - POST /login/GameSessionToken（path enum 6）
    - HTTP 回调 0x1402973B0 → 0x140297A40
响应:
  成功要求: HTTP 200 + JSON "Server"==本机 userid + "UserID"/"SteamID" 平台 ID 与客户端声称一致
    - 平台不符: "Failure to validate user provided platform ID %s from user %s. Expected %s"
  通过 → 0x1402400A0（Client authenticated / ClientAuthenticationComplete，Lua 事件）
  失败 → "[OnValidateGameSessionToken] AUTH_FAILED %s" → client 侧 0x14023FDBE:
    kick 0x94 ID_DST_GAME_SESSION_AUTH_FAILED
```
**Offline / LAN → `0x14023FD80` 放宽路径**
```
- 检查是否报了合法 userid，没有则警告 "Client did not report a valid userid: %s"
- 接受客户端声称的 userid（本地/缓存），不查 Klei
```

### 3.3 认证完成后的后续闸门（都在握手/加入路径上）
- **VERSION_MISMATCH**：服务器 `0x140244F25` / 客户端 `0x140245CE8`（build 号 747465，`Version Mismatch: Server: %i Client: %i`）
- **PLATFORM_MISMATCH**：服务器 `0x140244E83` / 客户端 `0x140245BEC`（`Platform Mismatch: Server: %u Client: %u`；g_NetManager+0x2A8 平台号，Steam 版=Steam / WeGame 版=Rail）
- 认证完成后：`[ClientObject] Initialized (authenticated) on server: guid=%s userid=%s netid=%s admin=%d`
- 此后所有 RPC（如 ReceiveRemoteExecute）**不再携带 userid**，只用 peer→NetId→ClientUser 映射（admin 校验 `+0x248`）

### 3.4 服务器侧（dedicated，`ServerLoginTokenViaSteam`）
用自己进程的 Steam 票据换 `cluster_token`（写 `cluster_token.txt`）；接待客户端时同样执行 3.2 的 ValidateGameSessionToken。

## 4. 安全要点

1. 握手携带的 KU_/OU_ 与 NetId 是**客户端自报**的；online 下主机必须经 Klei `/login/GameSessionToken` 把 token、userid、平台 ID 对上号后才放行。
2. GameSessionToken 是**会话级**（`TokenExpiry` 过期），Steam 票据不直接进游戏。
3. Offline/LAN 模式（+0x30B=0）跳过 Klei 验证，仅信客户端自报身份 —— 这是本地房/离线可绕过的根本原因，也解释了为何 LAN 房无法完成在线用户验证。
4. admin 是**主机侧策略**（adminlist / 主机自身 / 构造位 `+0x248`），不是客户端可声明的字段。
5. WeGame 与 Steam 同源：仅平台后端不同（SteamTicket↔RailTicket，`LoginViaSteam`↔`LoginViaRail`），Klei 账号体系与 GameSessionToken 校验两版共用。

## 6. 附录：脚本化登录（不开游戏直接登录 Klei）—— 已实测通过

`klei_steam_login.py`（位于项目根目录）完全模拟阶段一的 C 层行为，已对真实服务器验证成功。

### 6.1 实测过程
```
1. ctypes 加载 DST 自带 steam_api64.dll（flat API）
   steam_appid.txt=322330 声明 appid（Steam 票据绑定 appid，Klei 端按它校验）
2. SteamAPI_Init -> SteamAPI_SteamUser_v021()
   -> SteamAPI_ISteamUser_GetAuthSessionTicket(user, buf, 0x800, &len)
   实测拿到 234 字节会话票据（hex 大写，与游戏 0x140294400 的 "%02X" 一致）
3. POST https://login.kleientertainment.com/login/LoginViaSteam
   headers: Content-Type: application/json / Accept: application/json / User-Agent: DontStarveTogether/...
   body:
     {"SteamTicket":"<HEX>",
      "Game":"DontStarveTogether",      <-- 关键：是 DontStarveTogether（无空格）！
      "FriendlyHostDescriptor":"<desc>",
      "NoEmail":true}
   （TokenExpiry 缺省即省略——游戏内该值为 0 时整键省略）
4. HTTP 200 响应 JSON:
   {"SecurityTxt":...,"ErrorCode":"","Error":false,
    "Token":"pcl-usc^KU_...^DontStarveTogether^<b64>",
    "UserID":"KU_...","Username":"","AnalyticsJWT":"<JWT>",...}
```

### 6.2 踩坑记录
- 初次用 `"Game":"Don't Starve Together"` → 服务器返回 **E_UNKNOWN_GAME**（Error=true）。
  改为游戏代码 **`DontStarveTogether`**（来自二进制 `/login/auto/?Game=DontStarveTogether`
  字符串 0x140521132 及 WIN32_STEAM 平台表 0x1405466A0）后成功。
- steam_api64.dll 的 SteamUser 取接口导出名是带版本的 `SteamAPI_SteamUser_v021`。
- 响应里 `Username` 在本次为空串，UserID/Token/AnalyticsJWT 都有值。

### 6.3 结果物
- GameSessionToken 形如 `pcl-usc^<KU_id>^DontStarveTogether^<256bit b64>`（"pcl"=PC+"usc"=区域 + 游戏 + 密钥）；
- AnalyticsJWT 是 RS512 签名 JWT，有效期约 1 年（exp = iat + 31536000）；
- 该 Token 与游戏内 LoginViaSteam 返回的是同一产物，可直接用于后续
  /login/TokenPurpose 续期等 Klei 接口。

### 6.4 注意
- 前提仍是 Steam 客户端运行且已登录（票据本身必须来自 Steam）；
- 拿到的 Token 属于本机当前 Steam 账号；请勿外泄（等同于该账号的 Klei 会话）。

### 6.5 Token 寿命（实测）
- **GameSessionToken = 精确 60 分钟**：`/login/TokenPurpose` 响应带 `ExpirationTime` 字段，
  实测 = 签发时刻 + 3605s；过期后调用返回 `E_INVALID_TOKEN`（78 分钟前的 token 实测已失效）。
- **续期**：`/login/TokenPurpose` body 仅 `{"Token":<当前token>}`（C 层 type 6，
  func 0x140299300），返回全新 60 分钟 token——这就是游戏客户端加入服务器前做的"刷新"。
  脚本新增 `--refresh` 模式复刻该行为（实测 200 OK、返回新 Token）。
- AnalyticsJWT：RS512 JWT，`exp = iat + 31536000`（整 1 年），与 60 分钟 token 无关。
- 游戏感知：主菜单每次启动都重新 LoginViaSteam；进房前 TokenPurpose 续期，
  因此玩家无感"60 分钟过期"这回事。
- 对正常运行结论：脚本登录/续期与游戏会话互不冲突（实测在 DST 运行期间执行 6+ 次无影响）；
  Klei 会话追加式、不销毁旧会话；Steam 票据用完即 Cancel。注意别高频刷接口。

# 附:脚本实现对照与 Token 寿命(原 klei_steam_login_README.md,2026-10-26 并入)

## 用法
```
python klei_steam_login.py                 # 登录并打印 Token/UserID/AnalyticsJWT
python klei_steam_login.py --json out.json # 同时把 HTTP 响应原样存文件
python klei_steam_login.py --desc "mypc"   # 自定义 FriendlyHostDescriptor
python klei_steam_login.py --tokenexpiry 3600   # 显式带 TokenExpiry=<秒>
python klei_steam_login.py --refresh "<当前Token>"  # TokenPurpose 续期
```

## 实现对照(与 dontstarve_steam_x64.exe C 层一致)
| 步骤 | 游戏做法 | 脚本做法 |
|---|---|---|
| 票据 | `SteamUser()->GetAuthSessionTicket(buf,0x800,&len)` | `SteamAPI_SteamUser_v021` + `SteamAPI_ISteamUser_GetAuthSessionTicket` |
| 票据编码 | `"%02X"` 逐字节大写 hex(0x140294400) | `raw.hex().upper()` |
| appid | 进程身份 322330 | `steam_appid.txt` 写 322330(Steam 票据绑定 appid) |
| 端点 | `POST /login/LoginViaSteam` | 同 |
| body | `{"SteamTicket","Game","FriendlyHostDescriptor","NoEmail"[,TokenExpiry]}` | 同 |
| Game 值 | `DontStarveTogether`(无空格) | 同(踩坑:空格版返回 E_UNKNOWN_GAME) |
| 头 | Content-Type/Accept: application/json, UA DontStarveTogether/ | 同 |
| TLS | 系统 CA,无证书固定(OpenSSL 默认) | `ssl.create_default_context()` |

## 输出说明
- `UserID`:Klei 账号 ID(KU_ / OU_ 开头)
- `Token`(GameSessionToken):会话凭证,形如 `pcl-usc^KU_xxx^DontStarveTogether^<b64>`
- `AnalyticsJWT`:RS512 签名 JWT(约 1 年有效),含 KleiID/AuthProvider(STEAM)/Game

## Token 寿命(实测)
- **GameSessionToken 精确 60 分钟**:TokenPurpose 响应含 `ExpirationTime`,
  实测 = 签发时刻 + 3605 秒(足以覆盖 60 分钟 + 余量)。
  过期后任何接口调用返回 `E_INVALID_TOKEN`(实测:78 分钟前的 token 已失效)。
- 续期:`POST /login/TokenPurpose {"Token":...}` 返回全新 60 分钟 token。
  这正是游戏客户端"加入服务器前"做的事(C 层 type 6 请求)。
- **链式续期(2026-10-26 新实测)**:用续期得来的 token 再次 TokenPurpose 依然成立,
  已验证连续 ≥2 跳,且续期后的 token 可正常 Tick——多账号"免沙盒"路线的依据(见
  [多账号路线图](多账号路线图.md))。
- **同账号新登录会废旧 token(2026-10-26 新实测)**:每次新的 LoginViaSteam 会使
  该账号上一个 GameSessionToken 失效(E_INVALID_TOKEN),脚本自动重登可恢复。
- AnalyticsJWT 与 60 分钟无关:RS512 JWT,`exp = iat + 31536000` = 整整 1 年。

## 会不会影响正常游戏?(实测没有)
- 本脚本在 DST 正常运行期间被执行了 6+ 次(含多次登录与续期),游戏全程无掉线、
  无被踢、无冲突;Klei 登录会话是追加式(每次新签 token;服务端的注销只发生在显式
  Logout/LogoutAll,脚本从不调用)。
- Steam 侧:GetAuthSessionTicket 每次都是独立票据,脚本结束立即 CancelAuthTicket,
  与游戏进程内的票据互不干涉(各用各的 handle)。
- 唯一要克制的是频率:别做高频循环登录(可能触发 Klei 风控/限流),正常使用无影响。
