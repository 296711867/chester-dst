## 0. 一句话结论

**多账号不需要沙盒、不需要多开 Steam。** 依据是 2026-10-26 的实测:
`/login/TokenPurpose` 可以用旧 token 换新 token **链式续期**(已验证连续 ≥2 跳,
续期后的 token 可正常 Tick)。只要链条不断,日常挂机只需要纯 HTTP(Tick + 续期),
完全不需要 Steam 客户端在场——每个账号只需**一次性**在本机 Steam 登录,换取首个
GameSessionToken 存档,之后无限接力。

## 1. 将来的用户流程(每个新账号只做一次"人肉环节")

1. 在本机 Steam 客户端**切换登录**到该账号;
2. 跑一次登录脚本,把响应存成 `credentials\accounts\KU_xxxx\session.json`;
3. 之后由调度器每天替所有 session 各续一次期、各发该发的 Tick(账号间错峰几秒),
   全程不开 Steam、不开游戏。

**链条断了怎么办**:某账号超过 60 分钟没续上,token 过期,重做一次 ①② 即可,
日常其余账号不受影响(见 §4 L2 降级)。

## 2. session 文件按账号组织(目标结构)

```
credentials\
├── accounts\
│   ├── KU_ab12cd34\          # 账号键 = Klei UserID(每个响应都带,稳定,即 Tick 归属)
│   │   ├── session.json      # 完整登录/续期响应原样(现 .hb_auto_session.json 的多账号版)
│   │   ├── console.log       # 该账号心跳日志(现 hb_auto_console.log)
│   │   └── gifts.log         # 该账号礼物记录(现 klei_gifts.log)
│   └── KU_xy98zu76\...
└── index.json                # 账号清单:[{"key":"KU_..","alias":"主号","steam_hint":"邮箱前缀","enabled":true}]
```

选 KU UserID 而非 SteamID 做键:UserID 在每个 Klei 响应里都有,且是 `refresh_or_relogin`
换 token 后唯一能立刻自证的归属字段;SteamID 只在取票据时可打印,降为 `steam_hint` 备查。

## 3. 调度器形态:单进程、单线程、顺序轮询(否决多线程)

一轮 = 遍历 enabled 账号逐个跑"tick + 领礼",轮末 sleep 到下一轮(360s)。每账号心跳
间隔仍是 360s/次,对 Klei 服务端而言单账号节奏完全不变;循环内天然错峰。

否决多线程的硬理由(不是偏好):
1. `klei_steam_login.py` 的 `get_ticket` 内部有 `os.chdir` + 写删 `steam_appid.txt`,
   进程级全局操作,并发即竞态;
2. ctypes 的 `WinDLL`/SteamAPI 上下文非线程安全;
3. tick 请求毫秒级、间隔 360s,多线程零收益。

容量评估:每轮预算 360s;每账号常态耗时 ≈1 次 Tick(≈0.5s);最坏礼物风暴 =
MAX_CHAIN 200×0.35s = 70s + 榨干 5 次 Tick。**设计容量 10 账号 @360s**;
>10 账号建议 interval 提到 720s 或分批多进程(每批独立 credentials 子树)。

## 4. TokenPurpose 链断裂的降级阶梯

- **L0(常态)**:到期前 5 分钟 `refresh_or_relogin` 走 TokenPurpose,纯 HTTP,
  不碰 Steam——多账号日常零 Steam 依赖。
- **L1(续期失败)**:整轮重登一次。重登响应的 `UserID` **必须等于该账号目录的
  预期 KU**,不等 → 判定"Steam 当前登录的是别的账号",立即进 L2,且**不落盘**该
  响应(防 A 目录存进 B 的会话——多账号最危险的静默错配)。实测结论"LoginViaSteam
  使同账号旧 token 失效"意味着 L1 重登成功后旧 session 作废,直接覆盖 session.json。
- **L2(链断停摆)**:该账号 worker 停止,状态置 `NEED_STEAM_SWITCH`,控制台醒目
  输出"账号 <alias> 需要人工:在 Steam 切换登录到 <steam_hint> 后重试"。
  **绝不自动反复重登**(错误账号反复拿票既无意义又制造风控噪声)。
  其余账号不受影响,继续轮询。

## 6. 已知风险

- 多账号同 IP 的请求频率风控表现未知,沿用 360 秒节奏并错峰;
- 长假期(整天不续)必然断链,属预期成本,回 §1 重做一次人肉环节即可;
- 跨账号错配(把 B 账号的会话写进 A 目录)是最大静默风险,§4 L1 的 UserID 校验是硬门禁。

## 7. 实现记录(2026-10-26,控制面板 v3/v4 实际落地形态)

与上文设计的差异(以实现为准):

| 设计 | 实现 |
|---|---|
| 注册表 credentials/accounts/index.json | 项目根 `panel_accounts.json`(与设置同级,gitignore) |
| 调度器遍历 index.json | `Panel.registry_snapshot()` 每轮快照,勾选即时改注册表、下一轮生效 |
| 每账号独立 360s 相位 | **interval=每轮间隔**,一轮顺序处理所有启用账号,账号间错峰 3s(单账号节奏不变) |
| 领满 30 分钟复查 | 领满=跳过该账号本轮 tick,窗口每轮重算(恢复更及时,零网络成本) |
| NEED_STEAM_SWITCH 状态 | `paused_reason="mismatch"`,面板里把该账号**关→开勾选**即重试;重新「添加账号」同样解锁 |
| 添加账号走脚本 | 面板「添加账号」按钮:Steam 切号后点一下,面板代登录并存档(LOGIN_GATE 串行) |
| —— 新增 | 每日礼/自动开神秘箱按账号独立;礼物表跨账号聚合(带归属账号);EN/中文切换 |

未变的核心保证:单线程顺序轮询(无并发 SteamAPI)、L1 UserID 门禁(重登不符即暂停且**不落盘**)、
L0 日常纯 HTTP 零 Steam 依赖、每账号独立 SQLite。
