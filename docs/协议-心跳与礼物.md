# DST 与克雷同步游玩时间 / 出礼物协议

> 基于 `dontstarve_steam_x64.exe` 反汇编（image base `0x140000000`）  
> 焦点：客户端如何把「游玩时间」同步给 Klei Item Server，以及服务器如何回礼。

---

## 0. 一句话

客户端**不上传累计游玩秒数**。  
它只在本地用 `dt` 累加，每满 **360 秒** 向

`POST https://items.kleientertainment.com/clientitems/DST/Tick`

发一个几乎只有鉴权字段的 JSON：

```json
{ "Token": "<session/login token>" }
```

**是否掉落、掉什么、进度推进** 全在 Klei 服务端；客户端只消费响应里的 `GiftReceived`。

---

## 1. 相关端点（同一 Item Server 体系）

| 方法/路径 | 作用 | 请求体字段（客户端组装） |
|-----------|------|--------------------------|
| `POST clientitems/DST/Tick` | 游玩心跳 / 掉落礼 | **仅 `Token`** |
| `POST clientitems/DST/DailyGift` | 每日礼 | **`ClientToken`**（同 token 源，字段名不同） |
| `POST clientitems/DST/GetAllItems` | 全量库存 | `ClientToken`, `InventoryStateToken`, `EventHash`, `CheckTwitchEntitlements` |
| `POST clientitems/DST/SetItemOpened` | 标记礼物已开 | （item id + token 类） |
| `POST clientitems/DST/VerifyGiftingReceipt` | 礼物回执校验 | `{ "Receipts": [ { "UserID", "Key" }, ... ] }` |
| `POST clientitems/DST/OpenMysteryBox` 等 | 开箱/交易 | 各自 body |

基址字符串：`https://items.kleientertainment.com`  
相对路径与 `"/"` 拼接后走统一 HTTP 客户端（`0x140187720`）。

**专用服 exe 没有 `Tick` / `SendItemDropHeartbeat`**：心跳是**玩家客户端**行为，不是世界主机模拟。

## 2. 本地时间如何驱动同步

### 2.1 对象与周期

| 项 | 值 |
|----|----|
| 函数 | `SendItemDropHeartbeat` @ `0x140277ae0` |
| 每帧入口 | gifting update @ `0x140278020` |
| 累加器 | 管理器对象 **`this+0x08`**（`float` 秒） |
| 频率常量 | `float 360.0` @ `0x140554eb4`（**6 分钟**） |
| 输入 | `xmm1 = dt`（真实帧时间，不是游戏内天数） |

伪代码：

```c
// 0x140277ae0  (rcx=gifting/inventory mgr, xmm1=dt)
acc = this->timer_sec;          // +0x08
acc += dt;
this->timer_sec = acc;
if (acc < 360.0f) return;
this->timer_sec = acc - 360.0f; // 保留余量，避免漂移清零

// 然后构造 JSON 并 POST Tick
```

含义：

- 同步粒度 = **每在线实玩约 6 分钟问服务器一次**
- **请求里没有 `play_seconds` / `dt` / `session_time` 字段**
- 服务器若要做「游玩时长掉落」，只能靠：**每次成功 Tick ≈ +6 分钟有效游玩**（或服务端自己的 session/计时），而不是客户端上报精确秒数

### 2.2 发送前门控（gate）

`0x140278020` 先 `call 0x1402755e0`，失败则整段 update（含 Tick）直接跳过。

gate 检查（`0x1402755e0`）：

1. 某全局登录/在线状态 `call 0x140247ec0` 为真  
2. 标志 `byte [obj+0x30a] != 0`  
3. `qword [obj+0x2d8] != 0` 且其 `+0x18` 非空  
4. 对内部 key 表查询 magic `0x9440204e` 成功  

→ **未登录 / 离线 / 库存子系统未就绪时不会 Tick**，游玩时间不会按这套协议推进。

### 2.3 强制调试

Lua：`TheInventory:Debug_ForceHeartbeatGift("")`（`debugkeys.lua`，Ctrl+I）  
对应同一 heartbeat 体系，可跳过等 360s，立刻走一轮请求。

## 3. Tick 请求协议（客户端 → 克雷）

### 3.1 构造（`0x140277ae0` 成功分支）

```text
json = new object()                         // 0x1404d9d20
token_val = dup_string( global_auth + 0x100 ) // 与 DailyGift/GetAllItems 同源
json["Token"] = token_val                   // 注意字段名是 Token，不是 ClientToken
body = json_stringify(json)                 // 0x1404dae40

method = "POST"
path   = "/" + "clientitems/DST/Tick"
HTTP_Post(http_client = this+0x68, path, body, callback = 0x1402760c0)
```

### 3.2 请求体形态

```http
POST /clientitems/DST/Tick HTTP/1.1
Host: items.kleientertainment.com
Content-Type: application/json   (由 HTTP 层决定)

{"Token":"<login/session token string>"}
```

与对比：

| 接口 | Token 字段名 |
|------|----------------|
| Tick | `Token` |
| DailyGift | `ClientToken` |
| GetAllItems | `ClientToken` + 额外状态字段 |

**没有**在 Tick body 里看到：

- 游玩秒数 / 会话时长  
- 角色、世界、天数  
- 上次掉落时间  
- SteamID / UserID（可能在 token 或 HTTP 其它层隐含）  
- InventoryStateToken  

因此：**「同步游玩时间」在协议层 = 周期性带身份的空心跳**，不是上传时间戳计数器。

## 4. Tick 响应协议（克雷 → 客户端）

回调：`SendItemDropHeartbeat_Complete` @ `0x1402760c0`

### 4.1 成功条件

```text
success_flag (dl) == true
HTTP status (r8d) == 0xC8 (200)
JSON 解析成功，否则:
  "Error parsing JSON in SendItemDropHeartbeat_Complete"
失败日志:
  "[FAILED to send item tick heart beat %s:%i] %s"
  其中 %s 为 "Success"/"Failure" 文案，%i 为状态码
```

### 4.2 客户端实际解析的字段

代码路径（简化）：

```text
root = parse_json(body)
for each child node in root:
    if name == "GiftReceived" and type_tag == 5:   // 复合类型（object/array 容器）
        key_node = get_field(root_or_obj, "Key")
        if key_node && type_tag == 3:             // 字符串类
            key = get_string(key_node)
            enqueue_pending_gift_key(mgr, key)    // 0x140275ee0
```

可还原的响应形状（客户端最小消费集）：

```json
{
  "GiftReceived": {
    "Key": "<gift key string>"
  }
}
```

或服务端返回含多个子节点、其中某个名为 `GiftReceived` 的对象（客户端按子节点名扫描）。

**客户端不读取**（至少在这条 complete 里没有字符串引用）：

- 累计 play time  
- next drop 倒计时  
- 掉落表版本  
- 礼物 item_type / item_id（Tick 完成时只收 **Key**）

`Key` 进入管理器 pending 链表（`this+0x10/+0x18/+0x20` 一带）；后续在 update（`0x140278020` 后半）里打包/校验/进库存，并 `PushEvent("ms_updategiftitems")`。

### 4.3 与 DailyGift 响应对比

DailyGift complete（`0x140262930`）解析：

```text
Error? (type 6)
GiftReceived (type 5)
  ItemType (type 2 string)  → 调 Lua SetDailyGiftItem(item_type)
```

| | Heartbeat Tick | DailyGift |
|--|----------------|-----------|
| 触发 | 每 360s 实玩 | 登录/库存流程附近一次 |
| 请求 token 字段 | `Token` | `ClientToken` |
| 成功礼物字段 | `GiftReceived.Key` | `GiftReceived.ItemType` |
| 后续 | pending key → 库存/回执 | 主界面 ThankYouPopup |

同名 `GiftReceived`，**子字段不同**：Tick 用 `Key`，Daily 用 `ItemType`。

## 5. Key 之后：回执与进账

### 5.1 VerifyGiftingReceipt（`0x140277da0`）

当 pending receipt 队列非空（`this+0x58`）时：

```json
{
  "Receipts": [
    { "UserID": "<string>", "Key": <id/number or string> },
    ...
  ]
}
```

`POST clientitems/DST/VerifyGiftingReceipt`  
→ 防止客户端伪造「我收到了礼物」。

### 5.2 进游戏表现

```text
Key 入队 / 校验 / 写入库存镜像
  → ms_updategiftitems
  → giftreceiver:RefreshGiftCount()
  → TheInventory:GetClientGiftCount(userid)
  → hasgift → 礼物机 UI
  → 打开后 SetItemOpened(item_id) → clientitems/DST/SetItemOpened
```

礼物数量序列化有 **uint8 上限**（`%hhu` 截断日志）。

## 6. 协议时序总图

```text
[客户端主循环]
    dt
      │
      ▼
gifting_update (0x140278020)
      │ gate 失败 ──▶ 什么都不发
      ▼
SendItemDropHeartbeat (0x140277ae0)
      acc += dt
      acc < 360? ──▶ return
      acc -= 360
      │
      ▼
POST items.../clientitems/DST/Tick
Body: { "Token": "..." }          ◀── 无「时间字段」，只有身份
      │
      ▼
[Klei Item Server]
  用 Token 识别账户
  记录/累加本次有效心跳（≈6min 游玩）
  查掉落进度/冷却/活动
  返回 JSON（可能带 GiftReceived）
      │
      ▼
SendItemDropHeartbeat_Complete (0x1402760c0)
  200 + JSON OK
  若有 GiftReceived.Key → pending
      │
      ▼
(后续 update) 校验回执 / 合并库存 / ms_updategiftitems
      │
      ▼
Lua 礼物机表现 → SetItemOpened 回写已开
```

## 7. 「游玩时间同步」到底同步了什么

| 问题 | 结论 |
|------|------|
| 客户端是否上报总游玩时长？ | **否**（Tick body 无此字段） |
| 客户端是否上报本次 dt/秒数？ | **否** |
| 如何体现「玩得越久越可能出礼」？ | **周期性在线心跳**；服务端按 Tick 次数/自身计时推进 |
| 本地唯一时间常量？ | **360 秒** 轮询周期 |
| 权威掉落判定在哪？ | **Klei Item Server** |
| 身份如何绑定？ | JSON `Token`（与登录会话同源；Daily 用 `ClientToken` 同值源） |
| 主机/专用服是否代发 Tick？ | **否**（字符串/函数仅 steam 客户端） |

可把协议理解成：

> **Keep-alive + drop-roll poll**：每 6 分钟用账户 Token 问一次「有礼吗？」，  
> 而不是 `SyncPlayTime(seconds)` 这类显式时间同步 RPC。

## 10. 「主机」如何知道你在玩游戏？

先分清两个「主机」，否则容易混：

| 角色 | 是谁 | 和出礼物关系 |
|------|------|----------------|
| **A. 游戏主机** | listen host / dedicated server 进程 | **不负责**皮肤掉落 Tick |
| **B. 克雷 Item Server** | `items.kleientertainment.com` | **负责**心跳出礼 |

---

### A. 游戏主机：靠网络会话，不靠 Tick

游戏主机**不知道、也不需要**你的 `clientitems/DST/Tick`。  
它判定「这个玩家在玩」的依据是 **DST 网络连接状态**：

1. 客户端连上 → 分配 peer / userid  
2. `TheNet:GetClientTable()` 里能看到该 userid  
3. 事件：`ms_playerjoined` / `ms_playerleft`  
4. 断线 / timeout → 移出 client table  

证据：专用服二进制**没有** `SendItemDropHeartbeat` / `clientitems/DST/Tick`。  
主机侧礼物相关只有库存镜像同步（`GetClientGiftCount`、inventory notification），那是**账户库存结果**的转发，不是「计时出礼」。

可选的 **WorldOverseer**（`worldoverseer.lua`）是**分析/metrics**，不是出礼：

- 每 **5 分钟** `SendClientHeartBeat` → `TheSim:SendProfileStats`（`event = "HEARTBEAT"`）  
- 数据源：`TheNet:GetClientTable()` 里当前在线玩家  
- 发往 metrics（`dst.metrics.klei.com` 一类），**不是** Item Server 的 Tick  
- 字段含 `GameplaySessionID`、`character` 等；`play_t` 出现在玩家统计 dump，**不驱动皮肤掉落**

所以：

> 游戏主机知道你在玩 = **你还挂在它的 net client 列表里**。

---

### B. 克雷 Item Server：靠你客户端自己的 Tick

克雷**不靠游戏主机汇报「某某在玩」来出皮肤礼**。  
链路是：

```text
你的 steam 客户端进程
  game.cpp::Update(dt)          @ 0x14000a280
    → 若 cGame+0xe8 == 0（非提前退出路径）
    → gifting_update(dt)        @ 0x140278020
        → gate（已登录 + 库存就绪）
        → SendItemDropHeartbeat @ 0x140277ae0
            → 每满 360s POST /clientitems/DST/Tick {Token}
```

要点：

1. **调用点在 `cGame::Update`**，和是否已加载世界模拟（`game+0x28` sim）**无关**——gifting 调用在检查 sim 指针**之前**。  
   → 只要游戏主循环在跑且登录门控过，**主菜单挂机也可能累加 360s**（仍要过 gate；未登录则不会发）。
2. 请求**只有 Token**，没有「我在某主机上、某世界」字段。  
3. 克雷侧含义近似：**持有有效 Token 的客户端进程还活着，并周期性报到**。  
4. 游戏主机 / 专用服**不能**替你发这条 Tick。

gate（`0x1402755e0`）里的「在线」指的是：

```text
[auth_obj+0xa0] != 0          // 有登录相关对象
[global+0x118] != 0           // 另一处会话/token 指针
[obj+0x30a] != 0              // 就绪标志
[obj+0x2d8] 及其 +0x18 非空
内部 key 查询 0x9440204E 成功
```

这是 **Klei 账户登录就绪**，不是「已连上某台 DST 服务器」。

### C. 对照表

| 现象 | 谁知道 | 怎么知道 |
|------|--------|----------|
| 你在某房间里跑图 | 游戏主机 | TCP/UDP 会话 + client table |
| 你账号该不该掉皮肤礼 | 克雷 Item Server | 你客户端每 6 分钟 `Tick` |
| 分析用的 play_t / HEARTBEAT | metrics（经主机 WorldOverseer） | 主机扫 client table，5 分钟上报 |
| 主机上的礼物图标数量 | 游戏主机 | 库存 notification / `GetClientGiftCount`（结果同步，非计时） |

### D. 直接回答

> **主机是如何知道我们正在玩游戏的？**

- 若「主机」= **房间主机/专用服**：靠 **网络连接与 client 列表**，不靠出礼 Tick。  
- 若「主机」= **克雷出礼后端**：它其实**不问游戏主机**；是 **你的客户端**在进程活着且已登录时，自己每 360 秒用 `Token` 说「我还在」。  
- 两条线独立：你可以连着服务器但 Tick gate 失败（未就绪）→ 不出礼；也可以（理论上）在客户端主循环+登录就绪下 Tick，与是否在某世界无强绑定。
