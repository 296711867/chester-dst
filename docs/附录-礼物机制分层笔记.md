## L94

# 饥荒底层礼物机制

结论先说：**底层礼物不是世界实体，而是 Klei Item Server 账户库存里的“未打开皮肤物品”**。  
Lua 只做表现；真正的数据、同步、开启、鉴权都在 C++ 的 `InventoryManager` / `InventoryProxy` 和 Klei 后端。

---

## 1. 分层架构

```
┌─────────────────────────────────────────────────────┐
│  Klei Item Server                                   │
│  https://items.kleientertainment.com/clientitems/DST│
│  GetAllItems / Tick / SetItemOpened / OpenMysteryBox│
│  DailyGift / VerifyGiftingReceipt / ValidateItems   │
└───────────────────────┬─────────────────────────────┘
                        │ HTTP JSON + 签名校验
┌───────────────────────▼─────────────────────────────┐
│  C++ 客户端/主机                                     │
│  cInventoryManager  (本地库存镜像)                   │
│  InventoryLuaProxy  → Lua 全局 TheInventory          │
│  ItemServerLuaProxy → Lua 全局 TheItems              │
│  网络: inventory notification / gift items 序列化    │
│  事件: ms_updategiftitems                            │
└───────────────────────┬─────────────────────────────┘
                        │ Lua API
┌───────────────────────▼─────────────────────────────┐
│  Lua 游戏层                                          │
│  giftreceiver → player_classified → toast/popup/SG  │
└─────────────────────────────────────────────────────┘
```

`giftreceiver.lua` 注释写的 `GiftingManager.cpp` 在当前二进制字符串里**没有直接符号名**，实际对应的是：

- `cInventoryManager`
- `InventoryLuaProxy` / `TheInventory`
- `SendItemDropHeartbeat` + `ms_updategiftitems`
- `clientitems/DST/*` 后端接口

可以把它理解成：**Inventory 子系统里的 gifting 模块**。

---

## 2. 底层数据模型

礼物在底层就是账户库存里的一条 item，带“未打开”状态。

从 `InventoryLuaProxy` 暴露的字段可还原结构：

| 字段 | 含义 |
|------|------|
| `item_id` | 实例 ID（64-bit，`%I64u`） |
| `item_type` | 皮肤/物品类型名 |
| `modified_time` | 修改时间 |
| `box_build_override` / `box_message` | 箱子类展示覆盖 |
| `skin_custom` | 可自定义皮肤数据 |

关键查询/修改 API：

```text
TheInventory:GetClientGiftCount(userid)  -- 某玩家未开礼物数量
TheInventory:GetUnopenedItems()          -- 本地未开列表
TheInventory:GetUnopenedEntitlementItems()
TheInventory:GetAutoBoxItem()            -- 需自动开的箱子
TheInventory:SetItemOpened(item_id)      -- 标记已开（会上报后端）
TheInventory:GetFullInventory()
TheInventory:CheckClientOwnership(userid, item_type)
```

**“有礼物”的底层定义**：本地/主机侧库存镜像里，该 `userid` 存在未打开（unopened）条目；`GetClientGiftCount` 返回其数量。

## 3. 库存如何进入本地

### 3.1 全量拉取

登录流程：

```text
TheInventory:StartGetAllItems()
  → HTTP clientitems/DST/GetAllItems
  → 带 InventoryStateToken / EventHash / CheckTwitchEntitlements
  → 写入 cInventoryManager 本地缓存
  → HasDownloadedInventory() == true
```

相关字符串：

- `clientitems/DST/GetAllItems`
- `InventoryStateToken`
- `using inventory state token from cached file`
- `Cancelling Get All Items flow`

### 3.2 增量/实时掉落（真正的“送礼心跳”）

二进制里有完整 gifting 链路：

```text
SendItemDropHeartbeat
  → clientitems/DST/Tick
  → 解析 JSON (SendItemDropHeartbeat_Complete)
  → 更新本地 gift items
  → 推送 Lua 事件 ms_updategiftitems
```

关键限制/错误串：

- `Exceeded maximum serializable gift items; truncating %I64u to %hhu`
- `Exceeded maximum deserializable gift items; %hhu > %hhu`
- `Error parsing JSON in SendItemDropHeartbeat_Complete`
- `[FAILED to send item tick heart beat %s:%i]`

含义：

1. 礼物列表有 **上限**（序列化字段是 `uint8`，`%hhu`）
2. 心跳结果是 JSON
3. 成功后通过 **`ms_updategiftitems`** 通知 Lua

### 3.3 礼物回执校验

```text
clientitems/DST/VerifyGiftingReceipt
  body: Receipts
```

错误：

- `Error decoding gift receipt sender`
- `Error deserializing unverified gift receipt request`

说明存在 **receipt（回执）** 机制：不是客户端自己说“我有礼物”，而是服务端发、客户端/主机再校验。

### 3.4 主机与客户端同步

主机侧还有：

```text
inventory notification packet
Error deserializing inventory notification packet
Error receiving inventory notification for unknown item type: %u
cInventoryManager::DeserializeAppendItems ...
Exceeded maximum ... append inventory size
```

也就是：

1. 客户端/后端先认定物品归属  
2. 主机通过 **inventory notification / append items** 更新各玩家库存镜像  
3. 主机才能 `GetClientGiftCount(userid)`  
4. 再同步 `player_classified.hasgift`

专用服二进制有 `ms_updategiftitems` / `GetClientGiftCount` / `VerifyGiftingReceipt`，但没有 `SendItemDropHeartbeat` 和 `clientitems/DST/Tick`：  
**Tick 心跳偏客户端；主机更侧重收包、校验、给各 userid 计礼物数。**

## 4. “打开礼物”在底层做什么

Lua 动画和 Popup 都是壳。真正状态变更是：

```text
TheInventory:SetItemOpened(item_id)
```

引擎路径：

```text
SetItemOpened(item_id)
  1. 在 local inventory 查找 item_id
     失败: "SetItemOpened item not found in local inventory: %I64u"
  2. 请求后端 clientitems/DST/SetItemOpened
  3. 回调 SetItemOpened_Complete
     失败: "SetItemOpened_Complete item not found..."
  4. 本地标记 opened / 移出 unopened 列表
  5. 再次触发礼物计数刷新 → ms_updategiftitems
```

所以：

- **未打开**：在 unopened 集合里 → `GetClientGiftCount > 0` → 可显示 toast  
- **已打开**：`SetItemOpened` 成功后从 unopened 移除；物品仍归账户，只是不再当“礼物”

`auto_open_gifts` 模组直接调 `SetItemOpened`，就是在**绕过礼物机和动画，只做底层消礼**。

## 5. 开箱 / 每日礼 / 权益礼（同一库存体系）

底层同一套 Item Server，入口不同：

| 类型 | 后端/API | 引擎对象 |
|------|----------|----------|
| 普通未开皮肤礼 | 库存 unopened + Tick | `GetUnopenedItems` |
| 神秘箱 | `clientitems/DST/OpenMysteryBox` | `TheItems:OpenBox` |
| 每日礼 | `clientitems/DST/DailyGift` | C++ 调 `SetDailyGiftItem` → Lua |
| DLC 权益 | `GrantSkinDLCEntitlements` | `AddNewSkinDLCEntitlement` |
| 兑换码 | `RedeemCode` | `TheItems` |
| 交易/购买追加 | barter/purchase complete | `OnClientInventoryAppended` |

`skinsutils.lua` 里：

```lua
function SetDailyGiftItem(item_type)  -- C++ 回调进来
function GetDailyGiftItem()           -- 主界面 ThankYouPopup 取走
```

每日礼不是世界掉落，是 **Item Server 判定后写进 C++，再塞给 Lua 弹窗**。

## 6. 从底层到游戏内表现的完整链路

```text
[Item Server 发放/掉落]
        │
        ▼
clientitems/DST/Tick 或 GetAllItems / notification
        │
        ▼
cInventoryManager 更新 local inventory
        │
        ▼
PushEvent("ms_updategiftitems")          ← 引擎→Lua
        │
        ▼
giftreceiver:RefreshGiftCount()
  giftcount = TheInventory:GetClientGiftCount(userid)
        │
        ▼
player_classified.hasgift = (giftcount > 0)
        │  若靠近 giftmachine
        ▼
hasgiftmachine = true
        │
        ▼
GiftItemToast 可点
        │ RPC.OpenGift
        ▼
SG "opengift" + POPUPS.GIFTITEM
        │
        ▼
GetUnopenedItems()[1] → GiftItemPopUp 展示
        │ ~175帧后
        ▼

        │ HTTP
        ▼

```

关键约束仍在 Lua/玩法层：

- 必须有 `giftmachine`（科学机器/炼金/书架）  
- 不能危险/骑乘  
- 这些**不改变库存**，只限制“何时允许打开 UI 并调用 `SetItemOpened`”

## 7. 安全与信任模型

底层设计明显是 **服务器权威**：

1. **拥有权**  
   `CheckClientOwnership` / `ValidateItems` / `ValidateSignature`  
   签名无效会：`Skins signature was deemed to be invalid`

2. **开启权**  
   `SetItemOpened` 必须后端确认；本地找不到 `item_id` 直接失败

3. **礼物回执**  
   `VerifyGiftingReceipt` 防止伪造 receipt

4. **离线降级**  
   - `ForceLoadOfflineCache` / `HasSupportForOfflineSkins`  
   - `Not sending appended inventory items in offline mode`  
   - 离线不能完整走在线 gifting

5. **数量截断**  
   gift items / inventory / vanity 都有序列化上限，防包膨胀

---

## 8. 一句话定义“底层礼物机制”

> **底层礼物 = Klei 账户库存中 `opened=false` 的 item 实例。**  
> 由 Item Server 发放，经 `GetAllItems`/`Tick`/notification 同步进 `cInventoryManager`；  
> 主机用 `GetClientGiftCount(userid)` 暴露数量，并用 `ms_updategiftitems` 驱动 Lua；  
> 打开时 `SetItemOpened(item_id)` 回写 `clientitems/DST/SetItemOpened`，清除 unopened 状态。  
> 科学机器、拆盒动画、Toast 全是上层 UX，不负责权威数据。

## L140

# 底层如何判断“时间到了该发礼物”

结论先说清楚：

**本地客户端并不计算“玩够多久就发什么礼”。**  
本地只做一件事：**按固定间隔把游玩心跳报到 Klei Item Server**。  
**真正判定“时间到了、该不该发、发什么”在服务器端**（`clientitems/DST/Tick` / `DailyGift`）。

---

## 1. 本地唯一硬编码的时间：360 秒

在 `dontstarve_steam_x64.exe` 里，礼物心跳函数（约 `0x140277ae0`）逻辑是：

```text
acc = acc + dt          ; 对象 +0x08 的 float 累加器
if acc < 360.0: return  ; 常量 float 360.0
acc = acc - 360.0
POST clientitems/DST/Tick
```

对应反汇编要点：

```text
addss  xmm1, dword ptr [rcx+8]     ; 累加帧时间
movss  xmm0, dword ptr [360.0]
comiss xmm1, xmm0
jb     skip                         ; 未满 360 秒
subss  xmm1, xmm0                   ; 减去一个周期，保留余数
... POST "clientitems/DST/Tick"
```

所以：

| 项目 | 值 |
|------|----|
| 本地计时周期 | **360 秒 = 6 分钟** |
| 计时单位 | 真实帧时间 `dt`（float 秒） |
| 存储位置 | 管理器对象 `+0x08` 累加器 |
| 触发动作 | `POST clientitems/DST/Tick` |

这不是“发礼物间隔=6分钟”的最终规则，只是**客户端向服务器报到的最小粒度**。

---

## 2. 时间从哪来、怎么驱动

调用链：

```text
主循环 Update(dt)          ; xmm6 = dt
  → 0x140278020            ; Inventory/gifting 子系统 update
      → gate 检查（在线/鉴权等）
      → 0x140277ae0        ; 累加 360s 后发 Tick
```

`0x140278020` 会先过 gate（`0x1402755e0`），失败则不发心跳。gate 会检查：

- 在线/登录相关状态  
- 某标志位（对象 `+0x30a`）  
- 账号/token 相关指针非空  
- 以及一个内部 key 查询  

**离线或未就绪时，不会 Tick，也就不会因游玩时间推进礼物。**

---

## 3. Tick 之后：服务器才决定“发不发”

本地请求：

```text
POST clientitems/DST/Tick
body 含 Token 等
```

回调 `SendItemDropHeartbeat_Complete`（约 `0x1402760c0`）：

1. 要求 HTTP 成功且状态码 `0xC8`（200）  
2. 解析 JSON  
3. 找字段 **`GiftReceived`**  
4. 再取其中的 **`Key`**  
5. 把 key 放进本地待处理集合  
6. 之后在 update 里打包/同步，并推送 Lua：

```text
ms_updategiftitems
```

然后 Lua：

```lua
TheInventory:GetClientGiftCount(userid)
→ giftreceiver 更新 hasgift
```

也就是说：

```text
本地:  每玩满 360 秒问一次服务器
服务器: 根据账户累计游玩/掉落表/冷却/活动 决定 GiftReceived
本地:  若有 GiftReceived，写入库存并通知游戏
```

**“时间到了”的权威判定不在客户端。**

## 4. 和“每日礼”是两条时间线

### A. 游玩掉落礼（Heartbeat Gift）

- 驱动：游玩时每 360s `Tick`  
- 调试：`TheInventory:Debug_ForceHeartbeatGift("")`（`debugkeys.lua` Ctrl+I）  
- 结果字段：`GiftReceived`  
- 进游戏内礼物机系统（`GetUnopenedItems` / `hasgift`）

### B. 每日登录礼（Daily Gift）

- 接口：`clientitems/DST/DailyGift`  
- 响应后 C++ 调 Lua `SetDailyGiftItem`  
- 主界面 `GetDailyGiftItem()` → `ThankYouPopup`  
- 更像**自然日/账户日冷却**，不是 360s 游玩心跳  
- 请求函数在库存下载/登录完成路径附近触发，不是每 6 分钟一次

`WorldOverseer` 的 5 分钟 `HEARTBEAT` **只上报 metrics**（`play_t` 等），**不发皮肤礼物**。

## 5. 完整时序

```text
玩家在线游玩
    │
    │ 每帧 dt
    ▼
gifting_update(dt)
    │
    │ acc += dt
    │ acc < 360? ──是──▶ 返回
    │
    │ 否（满 6 分钟）
    ▼

    │

  - 读取该账号累计有效游玩/上次掉落/活动配置

      GiftReceived: [ { Key: ... }, ... ]  或空
    │

  - 有 GiftReceived → 记入本地 gift/inventory

    │

  - 靠近科学机器/书架才能打开
  - SetItemOpened 后再向服务器确认已开
```

## 6. 为什么体感像“按游玩时间送礼”

| 层级 | 做什么 | 是否决定“该发了” |
|------|--------|------------------|
| 客户端累加器 | 每 360s 报到 | 否，只负责问 |
| Item Server | 按账户游玩进度/冷却/表 | **是** |
| 主机 `GetClientGiftCount` | 给当前世界玩家同步数量 | 否 |
| Lua 礼物机 | 限制打开场景 | 否 |

所以玩家感觉是“玩一段时间出礼”，实际是：

1. 客户端保证**至少在线游玩**才会持续 Tick  
2. 服务器用这些 Tick（以及账号历史）做掉落进度  
3. 具体阈值/保底/池子在服务端，客户端看不到阈值表

本地能确定的只有：

- **轮询周期 = 360 秒**  
- **必须过在线 gate**  
- **服务器用 `GiftReceived` 回传结果**

## 8. 直接回答你的问题

> 底层是如何确定时间到了应该发送礼物？

1. **客户端**：用 float 累加真实游玩 `dt`，每满 **360 秒** 发一次 `clientitems/DST/Tick`。  
2. **服务器**：根据账号侧游玩/掉落状态判断是否产生礼物，通过 JSON 字段 **`GiftReceived`** 下发。  
3. **客户端收到非空 `GiftReceived` 后** 才更新本地库存并 `ms_updategiftitems`。  
4. **本地没有“玩满 X 分钟必得礼”的掉落公式**；360 秒只是心跳粒度。  
5. **每日礼**是另一条 `DailyGift` 日刷新逻辑，不走这 360 秒累加器。

如果你要继续挖，下一步最有价值的是抓一条真实的 `Tick` 请求/响应 JSON，看 `GiftReceived` 之外还有没有进度字段（例如 total play seconds、next drop 等）——那部分只在服务端或响应体里，不在本地 Lua。
