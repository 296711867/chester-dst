# 情报:创意工坊挂礼物 mod 调研 × 历史礼物可行性(2026-10-29)

> 起因:用户反馈"别人之前在游戏里领的礼物,面板查出来 0 个"。调研工坊挂礼物 mod 是否有
> "查看历史礼物"功能,以及有没有别的路子拿到历史。

## 一、调研方法

steamcommunity 工坊搜索 `gift` / `礼物` / `领取`(appid 322330)→ 39 个候选,人工筛出 8 个
"挂机领礼物"类 mod 逐个抓详情页分析。(网络备注:steamcommunity 直连出口被 429 限流时走本机
Clash 7897 出口 + 10~30s 间隔可解;moli 内核渲染不了 steamcommunity,换 curl+正则解析。)

## 二、结论 1:没有任何 mod 能查"安装前"的历史礼物

8 个挂礼物 mod 全景:

| mod | id | 历史功能 |
|---|---|---|
| 挂机自动领取礼物 AutoOpenGift | 3801660727 | **唯一带历史面板的**:F8 统计面板(本周数量/登录vs时长分类/剩余可领/领取记录列表含稀有度),**本地记账持久化跨天累计** |
| auto_open_gift(自动挂机开礼物) | 1309401477 | "提示收到的礼物数量和时间"=运行期会话提示,不落历史库 |
| Gift_Opener(updated) | 2479513334 | 无(纯自动开+上帝模式) |
| Idle Gift Opener | 1807205284 | 无 |
| Auto Open Weekly Gift | 3422869992 | 无——**但描述指路:"For gift history, please visit Klei's transactions page [accounts.klei.com]"** |
| 自动领取每日礼物 auto_daily_gift | 3764412852 | 无(纯自动开每日礼) |
| Open daily gift automatically | 3351381834 | 无 |
| [Abandoned]Auto Open Gift | 1210706609 | 无 |

**关键洞察**:唯一做了历史功能的 AutoOpenGift,其架构与 Chester 面板完全同构——**mod 自己
本地记账**(描述原文:"统计记录持久化保存到本机,跨天累计")。连 mod 作者也没从服务器拿到历史,
只能记"mod 运行期间"发生的领取。**mod 装上之前的领取,对它同样是 0。**

即:Chester 面板"查不到接入前的历史"不是实现缺陷,是全生态共识性的天花板。

## 三、结论 2:新线索——Klei 网页账号门户有 transactions 页(未开发的金矿)

Auto Open Weekly Gift 作者指路的 **accounts.klei.com** 实测结构(2026-10-29):

- `GET /account/transactions` → 302 `/login?goto=...`(**页面真实存在,登录后可见**);
- 门户导航:`/account/info` · `/account/rewards` · `/account/transactions` · `/account/settings` · `/account/game/list`;
- 登录方式:`/login/steam` → 302 `steamcommunity.com/oauth/login?client_id=4F6D9712&redirect_uri=https://accounts.klei.com/sso&response_type=code`(**Steam OAuth2 网页流程**,非游戏票据);
- 交易页为服务端渲染(无独立前端 JS bundle,数据随 HTML 出),接口细节需登录后抓包。

**与既有结论的关系**:docs/协议-Klei接口总表.md §2.8"Klei 无礼物历史端点"结论**仍然成立**——
那是**游戏客户端 API 面**(items/login/lobby)。accounts.klei.com 是**网页门户另一张脸**,游戏
客户端不调它,所以 exe 字符串挖掘挖不到。两张脸合起来:历史数据可能存在于网页侧。

**若要 Chester 集成(待拍板的后续方向)**:
- 可行路径:用户在面板里走一次 Steam OAuth 网页登录(需 steamcommunity 浏览器会话,半人工一次)
  → 拿门户会话 cookie → 拉 `/account/transactions` 解析 HTML → 回填面板本地库的"接入前历史";
- 成本:网页会话管理(过期续期)、HTML 结构解析、OAuth 流程嵌入;
- 收益:解决"别人接入前领的礼物查不到"的根问题;
- 风险:网页非公开接口,结构可能变;OAuth 会话与游戏票据体系独立。

## 四、给用户的直接答复

1. 工坊 mod 们也查不到安装前的历史——这不是我们做得差,是 Klei 游戏侧根本不给;
2. 唯一例外线索是 Klei 自己的网页账号页(accounts.klei.com → transactions),要登录才能看,
   是未来潜在的补历史入口(需要做网页登录集成,属于新功能开发)。

## 五、追加(同日):衣柜数据反推礼物来源——三档置信度分类器(实测成立)

用 `_probe_items.py`(只读探针)拉真实 GetAllItems(1063 件)分析,**三个机制级发现**:

1. **Modified = 物品进入衣柜的时刻**(非"最后修改"):面板流水 3 件礼物对照,领取时间与
   Modified 差 ±2.4 秒内。开礼即刷新;此账号未编织/未交易的旧物品 Modified 停在 2018 年不动。
2. **稀有度即获取通道**:Heirloom Distinguished/Elegant = **编织专属**(礼物永不掉,该账号 11 件
   全部孤立时间戳,符合手动编织行为);Loyal=忠诚奖励码 / Timeless=单机遗产 / Event=活动领取
   (18 件全 Modified=0)/ Character=角色捆绑——全部**确定非礼物**。
3. **ItemID 高位前缀 ≠ 发放批次**(同前缀 75 件跨度 17.8h/20 天,是分片/纪元种子),不可用作来源信号,弃用。

**分类器(按置信度三档)**,实测该账号:

| 档 | 判据 | 件数 |
|---|---|---|
| 确定非礼物 | 稀有度 ∈ {Loyal,Timeless,Event,Character,Heirloom*} | 93 |
| 面板确认礼物 | 在本地礼物流水(±分钟级 Modified 对账) | 3 |
| 礼物池(高概率礼物) | Common/Classy/Spiffy/Distinguished/Elegant(礼物唯一可掉稀有度带) | 970 |

礼物池内部再分:**孤立时间戳 ~378 件**(单次到账即开,单次礼物)与**批量簇 ~592 件**
(≥3 件/60 秒窗口;挂机囤礼后连开的典型形态,月份热力集中在 2021-02/2020-10 等寒暑假挂机期,
佐证)。**残余不可分**:囤礼连开 vs 神秘箱连开 vs Twitch 掉宝 vs 市场购入——同批量形态,
衣柜数据无法 100% 分离;单件市场购入与单次礼物同为孤立时间戳,同理。要权威逐笔来源,
唯一路径仍是 accounts.klei.com transactions(见 §三)。

**结论**:纯挂机账号的衣柜里,礼物池稀有度物品 ≈ 礼物开出来的(误差=偶发购入/掉宝);
"哪些是礼物"可以分到 ~90% 置信度,且每件带获取时间(Modified)。可做成面板功能
(GetAllItems 快照+分类+衣柜页),待拍板。
